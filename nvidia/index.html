3The 11 concepts you must be able to explain

Hardware and network
1. Why GPUsThousands of cores doing matrix math in parallel, fed by very fast on-package memory (HBM). GPUs work as a team: one slow GPU slows the whole job. Every infra job exists to keep expensive GPUs busy and healthy.
2. NVLink / NVSwitch / NVL72NVLink is a fast GPU-to-GPU link inside a server (8 GPUs). NVL72 extends it to 72 GPUs across one rack, so they act like one big GPU.
3. DGX vs HGXDGX: NVIDIA's complete server plus software. HGX: NVIDIA's GPU board inside Dell, HPE or Supermicro servers, where the customer builds the software stack. Most enterprises buy HGX (Maaz).
4. The 4 networks in a GPU clusterManagement/BMC (out-of-band) · provisioning (PXE boot) · front-end (SSH, users, storage) · back-end (GPU-to-GPU, one network card per GPU, 400G+). The back-end must never drop packets.
5. InfiniBand vs RoCE, and "non-blocking"InfiniBand: lossless by design, NVIDIA's standard. RoCE: RDMA over Ethernet, cheaper and familiar, but needs PFC and ECN tuning to avoid drops. Non-blocking (1:1) means switch uplinks equal downlinks, so all GPUs can talk at full speed. Training needs this.
Storage and Kubernetes
6. Storage: pick it for speed updatedObject storage (S3/GCS): cheap and remote, so model weights load slowly. File storage (Lustre, VAST, WEKA, DDN): shared and fast, needed for training checkpoints written by every node at once. Block / local NVMe: fastest, one node only. For inference the problem is model load time: cache weights on local NVMe or a shared cache close to the GPUs so new pods start in seconds, not minutes (Vishakha).
7. GPUs in KubernetesThe GPU Operator (Helm) installs drivers, the device plugin and DCGM monitoring. Pods ask for nvidia.com/gpu: 1. MIG splits one GPU into up to 7 isolated slices. The Network Operator adds RDMA networking. Topology-aware scheduling: place a job's pods on GPUs and nodes that are close (same NVLink domain, same network switch) so they talk fast (Vishakha).
Models and inference
8. Inference, and how to make it faster updatedPrefill (read the prompt) is compute-heavy; decode (generate tokens) is memory-heavy. vLLM is the standard server. Metrics: tokens/sec, time to first token, cost per token. Faster: quantization (FP16 → FP8 halves memory; INT4 quarters it, with a small accuracy loss) · continuous batching · prefix caching · tensor parallelism across GPUs · split prefill and decode (llm-d, Dynamo) · autoscale on queue length, not CPU. Your job is to turn a 5 s response into 2 s (Vishakha).
9. Debugging a slow jobCheck DCGM (errors, temperature, clock throttling), compare node speeds to find the slow one, run NCCL tests between node pairs, check network link speed and errors. Remove the bad node and re-test (Krati's daily work).
10. Model basics (100-level only) newA model is layers of weights. Memory = parameters × bytes (FP16 = 2, FP8 = 1), so a 70B model in FP16 needs 140 GB. Training = forward and backward passes over data, with all GPUs syncing gradients (all-reduce, which is why the network matters). Inference = forward pass only. The 3 workloads: preprocessing (CPU and storage heavy), training (GPU and network heavy), inference (latency heavy).
11. Kubernetes operators and security newOperator = a custom resource (CRD) plus a controller that keeps reality matching it. The GPU Operator is one. Security beyond IAM: RBAC, NetworkPolicies, Pod Security Admission, and admission control with OPA Gatekeeper (e.g. block privileged pods, or require a team label on GPU pods), plus image scanning and signing (Vishakha).

Fundamentals
GPU vs CPU: why did AI move to GPUs?Concept 1. Add: GPUs work as a distributed team, so network and topology matter as much as raw speed.
Front-end vs back-end network: why separate them? (★ Maaz)Concept 4. User traffic is bursty; GPU traffic must be lossless and full speed.
InfiniBand or RoCE for a new cluster?Concept 5. "It depends on scale, team skills, cost and multi-tenancy." Then pick one and justify it.
MIG vs giving the whole GPU? (★ Maaz)MIG for small models and many tenants, with real isolation. Whole GPU (or several) for large models and training.
Object, file or block storage for an ML platform? (★ Vishakha)Concept 6: object for the data lake and model registry, parallel file system for training and checkpoints, local NVMe cache for fast model loading.
How many GPUs to serve a 70B model?FP16: 140 GB, so 2× H100 (80 GB each). FP8: 70 GB, so it fits on one H200 (141 GB) with room for the KV cache. Then add replicas for traffic.
Model serving and optimization (★ Vishakha: most asked)
How do you deploy a model on Kubernetes, end to end?GPU node pool + GPU Operator → vLLM container → weights pulled from object storage and cached on local NVMe → Deployment requesting nvidia.com/gpu (tensor parallel if it needs more than 1 GPU) → Service / gateway → autoscale on queue length or latency → DCGM + Prometheus dashboards.
Responses take 5 s. Get them to 2 s.Measure first: time to first token (prefill) vs per-token time (decode). Then: quantize to FP8 → tune batching → prefix caching for repeated prompts → tensor parallelism → a GPU with more memory bandwidth (H200) → split prefill and decode at scale (llm-d, Dynamo).
A new pod takes 10 minutes before it serves. Fix it.Break down where the time goes: image pull (pre-pull, smaller image) → weight download (local NVMe cache, faster storage, streaming load) → loading onto the GPU. Keep warm replicas for spikes.
What is quantization, and what does it cost?Storing weights in fewer bits (FP16 → FP8/INT4). Less memory, more speed and cheaper serving, with a small accuracy drop, so always re-run the evals. Show your Lab 1 numbers.
Troubleshooting
A 10-node job normally takes 30 min, today it took 1 hour. Find the cause. (★ Krati)Concept 9, step by step: DCGM health → per-node speed → NCCL tests on node pairs → network counters → recent changes → remove the node, re-test, file an RMA.
NCCL bandwidth is half of what's expected. Why?NCCL fell back to TCP (check NCCL_DEBUG=INFO), network link running at lower speed, GPU paired with a far-away network card, MTU mismatch, Ethernet pause storms.
GPU shows 100% utilization but output is slow."Utilization" only means something is running. Check throttling (heat or power), memory bandwidth, and whether the CPU or data loading is the bottleneck.
