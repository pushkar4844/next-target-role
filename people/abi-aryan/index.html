1Her method

"Stop collecting courses, videos and repos. Start practising."Take one inference request and follow it end to end. Don't stop until you can answer each question with evidence:
The 6 questions1) How does the serving engine schedule it? 2) Where does its KV cache live, and who owns that memory? 3) Which component moves data between CPU, GPU and network? 4) What exact CPU, GPU, memory and network paths does it touch? 5) Why did the scheduler put it on this hardware and not another? 6) What do the traces actually prove is the bottleneck?
Her 6-step order (kernels last)1) Request path: gateway → router → scheduler → engine → GPU. 2) Prefill vs decode: two workloads in one word. 3) KV cache as a first-class resource. 4) Batching, queues, SLOs (TTFT, TPOT). 5) Parallelism: data, tensor, pipeline, expert. 6) Only then CUDA, kernels, compilers, "when you know which millisecond you are buying."
Her philosophy"Don't accept the abstraction. Understand what the system actually does. Take it apart. Measure it." Good pipeline design starts at observability and platform engineering, not at a pull request into vLLM. That's where your DevOps/SRE background is an advantage.
The role she describesAn "inference SRE / performance engineer" who sees across software (vLLM/SGLang config), hardware (DCGM, thermals, drivers), network (InfiniBand, RoCE) and storage (NVMe, cold model loads). When p95 TTFT jumps from ~180 ms to 2.1 s while GPU utilization looks fine at ~85%, each team says "my layer is healthy". The problem lives between them.

      serverAddress: http://prometheus:9090

4Her ideas, in short

GPU utilization is not goodputA server can look 80% busy and still miss latency SLOs. Wait time explodes as utilization nears 100% (Kingman's formula: at 30 ms service, 0.03 s wait at 50% → 0.12 s at 80% → 0.57 s at 95%). Two teams on similar hardware paid $97 vs $0.38 per million tokens. Scale on SLO violations and KV pressure, not on "the GPU looks hungry."
Same GPU, 3.3 s vs 39 sIdentical weights, card and code; the request shape did it. Prefill is compute-bound, decode is memory-bound. Split TTFT from inter-token latency; never trust one p50.
Agents OOM at 62% utilization ($27k weekend)Stateless RAG drops context; agents hold HBM for the whole 50–70-turn thread with tool retries. 7 of 12 replicas died. Fix: cap context growth, time out stuck agents, price per solved task.
KV cache needs a directoryOn one GPU, KV is an allocator. Across a cluster it's a phone book: who has this prefix, how stale, what does a move cost. Mooncake, LMCache and cache-aware routing solve this. Hashing users to GPUs without it wastes prefixes.
Mooncake's 3 cache tiersL1 GPU HBM (fast, tiny) → L2 CPU/host memory → L3 Mooncake Store: DRAM and SSDs across the cluster over RDMA, giving global prefix reuse. Result: lower TTFT and higher throughput on the same hardware.
NIXLNVIDIA's open-source data-movement library for disaggregated serving: async, zero-copy KV transfers between prefill and decode workers across HBM, DRAM and NVMe/object storage, over RDMA, UCX, GPUDirect and EFA. Used by vLLM, SGLang and Dynamo.
CPU throttling starves GPUsUtilization drops while TTFT spikes because the container's CPU is throttled (cgroups). Put GPU utilization, serving latency, cgroup throttling counters, host queueing and CPU pressure on one timeline.
Power capsTwo servers with the same utilization can react very differently to a power cap. Standard dashboards can't tell you which survives. Power, cooling, KV, queues and retries are one coupled system.
SkyPilotOne portable job spec across Kubernetes, Slurm, clouds and on-prem: capacity search, spot recovery, cost-aware placement. Alternatives: dstack, Ray.
Example of a finished projectA student's final project: Gemma 31B FP8 on vLLM, 2× H100 on Lambda, Envoy AI Gateway token budgets, llm-d router (prefix match first, split prefill/decode only when 2,048+ uncached tokens), LMCache for KV transfer, a warm-controller before traffic, KEDA scaling. A good bar for your Project 2.

5Reading list she gave (for people moving from Ops/Platform)

Her advice: don't skim. For each concept, find a real system that implements it, read its code or architecture docs, and try to break it. She assumes distributed systems basics (CAP, consistency, consensus) and some Kubernetes.

Papers
  • Mooncake: KVCache-centric disaggregated serving · repo · docsFocus on the Transfer Engine protocol, not just the architecture.
  • Llumnix: dynamic scheduling for LLM serving · repoThe live migration protocol is the interesting part.
  • Preble: distributed prompt schedulingCache-aware distributed scheduling.
  • DCQCN: congestion control for RDMA (SIGCOMM 2015)"This math is worth working through." It's the basis of RoCE ECN tuning.
  • Borg · OmegaScheduling theory that carries straight over to GPU clusters.
  • Rail-only (Meta): low-cost network for training LLMsThe reality of GPU cluster networking.
  • Gavel: heterogeneity-aware scheduling · Pollux · Sia · ThemisHer Oct 17 reading list: GPU cluster scheduling.
