1Key points

1. Managed-service DevOps is now commodity; AI infra is "back to basics".Anyone can prompt an AI to write Terraform for 10 customers. In AI infra there's no managed layer: compute, network and storage fundamentals are the job.
2. Learn it in this order: bare metal → network → storage → Kubernetes → GPU drivers → slicing.Each layer is one study block. Start from "boot a server", not "click a GPU in the console".
3. Infra is sized in megawatts and GPU count, not dollars.People talk about "a 3 MW / 15 MW data center" or "this many GPUs".
4. Training and inference need different infrastructure.Training spans nodes: needs a non-blocking lossless back-end network and a parallel file system for checkpoints. Inference usually fits in one node; normal storage is fine.
5. Get hands-on hardware by the hour.NVIDIA's own platform rents GPUs per hour (student discounts exist); a DGX Spark is a desk-sized option.

3In detail

Why "back to basics"
Managed services hide the hard partCreating a cluster on AWS or Azure hides the control plane, storage and network plugins they engineered. A new hire at his company generated all Terraform from Claude and deployed it for 10 customers without thinking. That work is now "prompt → implement". Real value is understanding what's behind it.
FundamentalsNetworking, storage, compute. "If you've ever installed an OS from a CD, you can grow in this industry." Then the 4th layer: the application.
Layer 1: bare metal orchestration
Booting at scaleServers boot via PXE (remote boot), using DHCP, DNS and TFTP services. With 100, 150 or 1,000 nodes you can't mount ISOs one by one; you need a tool that tracks state. His best tool so far: MAAS (Canonical, open source). It supports tenancy and onboarding nodes onto different networks. Any "GPU factory" conversation starts here.
DGX vs HGXDGX: NVIDIA's full stack (rack, OS, Kubernetes or Slurm layer) managed by NVIDIA. HGX: NVIDIA's GPU board inside Dell, HPE or Asus servers that the OEM tests and benchmarks; you build the solution around it. Smaller orgs buy 3–4 HGX boxes for local AI or agent work. He suggests learning on the HGX side: that knowledge is what makes NVIDIA want you.
His recent build159 GPU nodes × 8 H200 (HGX) for an Abu Dhabi client. They chose HGX over DGX for cost and to resell capacity: 2 nodes to one customer, 4 to another. Bare-metal management (MAAS, PXE, network definitions) was the key skill.
Layer 2: networking
Networks per nodePXE: one-time boot, 1 Gbps is enough; can be merged with management. Front-end / management: SSH, exposed services, Kubernetes load balancer IPs. Storage connectivity. Back-end: GPU-to-GPU; every GPU brings its own NIC (400/800 Gbps) up into the fabric.
SizingWhen proposing a solution you state the NICs: e.g. per node 2× 25/100G front-end + 8× 400G back-end. That decides the whole fabric for, say, 32 nodes.
Subscription ratio (his math)2 nodes × 8 × 800G = 16 ports. A 16-port switch is full; a 3rd node needs another switch layer, and uplinks must carry 16 × 800G if everyone sends at once. Fabric designers check: if all GPUs send together, what's the largest cluster I can build?
LosslessTraining sends each layer's output to the next GPU; retransmits like TCP stretch training time. InfiniBand transfers without errors; on Ethernet, ECN (congestion signalling) and PFC (priority flow control) make the back-end lossless.
Multi-tenancyOn bare metal there's no "create a VNet" button. Learn VLAN/VXLAN and network segregation, and the fabric vendors: Cisco, Arista, Dell SONiC.
Layer 3: storage, training vs inference
GPU vs CPUBoth have RAM and cycles, but GPU memory is HBM, very high bandwidth, so data moves at GPU compute speed instead of the CPU waiting on disk → RAM.
TrainingAll layers and data must sit in GPU memory at runtime. One node maxes at 8 GPUs, so big models span nodes, which then must talk constantly over the fabric. Checkpoints written to storage without parallel I/O leave GPUs waiting. Hence parallel file systems (Lustre) and vendors like DDN and VAST.
InferenceThe model is already trained; it only generates responses, usually not across a big cluster, so normal storage is fine. Most companies outside the few model-training labs run inference, so that's where most infra jobs are.
Layers 4–5: Kubernetes, drivers, GPU sharing
Kubernetes install is your jobNo managed service: kubeadm, k3s, etc. Understand masters, the etcd cluster, everything Azure hides. He learned from Mumshad Mannambeth's KodeKloud course.
GPU drivers"Just Helm charts" (GPU Operator), installed per configuration. Then: allocatable resources: where they're listed, how many are left, how they're assigned.
RDMA into podsA normal pod gets one NIC from the pod CIDR. A GPU pod also needs back-end NICs, installed through a CNI (RDMA), so you must plan how to expose and use them in Kubernetes.
Three ways to share GPUsGPU passthrough to VMs: pass PCI devices (IDs, product ID) and include the driver in the image. vGPU: virtual GPUs to separate VMs. MIG: physically splits one GPU by memory size and SM (compute) cores into profiles, so one GPU serves several workloads. NVIDIA's tooling here is ahead of others (AMD uses ROCm).
Model sizingParameters × bytes per parameter = memory. Small models (~27B) fit on one GPU or a MIG slice; profile accordingly.
Learning and hardware
Where to readNVIDIA blogs. Consolidated material on storage and fabrics barely exists; you learn it on the job. For interviews, be able to explain parallel file systems and when they're needed.
HardwareNVIDIA's platform rents full servers per hour; with a college ID, students get discounts or free time (a 2.5-year-experience colleague got a B300 for a month). Buying: a DGX Spark is enough to play with.
Market noteIn the Middle East, Azure has ~70–80% share (e.g. First Abu Dhabi Bank) because of data sovereignty regions; AWS presence is small.

4Corrections

FP8 is 1 byte per parameter, not 4. FP32 = 4, FP16/BF16 = 2, FP8 = 1, INT4 = 0.5. So a 27B model in FP8 is ~27 GB of weights (plus KV cache), which matches his "~30 GB" example.
H200 memory bandwidth is 4.8 TB/s (nvidia.com). The 1.8 TB/s figure he quoted is NVLink bandwidth per GPU on Blackwell, a different link.
The hourly platform he linked in chat isn't in the transcript. NVIDIA's per-hour GPU service is Brev; confirm with him.
