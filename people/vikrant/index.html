1How he thinks: the 5-layer sizing order

This is the order an SA walks through for any GPU/HPC requirement. Use it as your discovery script and your interview answer structure.

#LayerQuestions to ask the customerWhat decides it
1ProcessingCPU or GPU? Which GPU? How much CPU and memory per GPU does the job need?Job profile → instance family (e.g. P5 / P6)
2MemoryHow much RAM? Does it fit in system memory (~2 TiB on P5/P6), or do you need scratch space?"2 TB of RAM is peanuts for HPC" → local NVMe scratch
3StorageRead-intensive or write-intensive? How many IOPS? Which data is read-only (libraries, packages) vs written (outputs, checkpoints)?Split the job: read-only on one file system, writes on another; scratch on NVMe RAID 0
4NetworkHow much bandwidth? Does it need EFA (RDMA)? Is everything in one AZ and subnet?One AZ + one subnet + cluster placement group; EFA isn't routable
5CostOn-demand, reserved capacity, or longer commitments? How long does the project run?Performance costs money: check the efficiency of each choice
"The more you look at each level, each layer, you have to go and fine-tune it." Then go deeper: learn what InfiniBand is to understand EFA, what the CUDA driver does, and what RDMA is.

3In detail

Storage: split the job by read vs write
Read-only partsPackages and libraries needed to run the job are only read. Put them on a read-optimized file system: FSx for NetApp ONTAP or FSx for OpenZFS. In his experience they cost much less than FSx for Lustre (he estimated about a quarter).
Write-heavy partsFor maximum write IOPS use FSx for Lustre. It stripes data across storage servers (like RAID 0), so a bigger file system is faster.
Scratch on local NVMeGPU instances come with local NVMe instance-store disks (about 30 TB on P5/P6). Create one file system across them with RAID 0 (striping) for speed; RAID 1 defeats the purpose. It's ephemeral: if the instance goes, data is lost. So process on NVMe, then write the final output to FSx or S3.
When EBS is too slowNeed very high IOPS (he said 65,000+)? Use instance-store NVMe rather than EBS volumes. See the gp3 numbers under Corrections.
Performance costs moneyA big Lustre file system can cost $1,000–$10,000 a week even when idle, so weigh efficiency, not only speed.
Network
Same AZ, same subnetKeep compute and file system in one AZ for maximum bandwidth and no inter-AZ data charges. Use placement groups to keep instances physically close.
EFAAWS's RDMA network for HPC and ML. EFA traffic can't be routed, so it doesn't cross subnets, AZs or regions; everything must sit in one subnet and AZ. It's AWS's equivalent of NVIDIA InfiniBand: learn InfiniBand to understand EFA.
Customer Q&A, as he answers it
"Why can't we use S3 as a file system?"HPC needs very fast reads and writes, and S3 isn't POSIX-compliant: no file permissions, no symlinks. Installed packages contain .so (shared library) files that rely on symlinks, so they break. Use S3 for read-only data; or create FSx for Lustre linked to S3 with a data repository association (DRA), run the project, export results to S3 (cheap), then delete the file system to stop paying. For small read-only files without symlinks, S3 Express One Zone (single AZ) works.
"What problems do customers hit?"1) They delete the file system straight away. Unmount it from every compute node first, then stop or delete. 2) Big GPU instances take 6–7 minutes to start, so bake a custom AMI to cut startup time. 3) These instances cost on the order of $100–150 an hour on-demand (his figure), and capacity is scarce. Use an On-Demand Capacity Reservation (ODCR) to hold them for a set time, and work with the account team on discounts: 1-year commitments help, 3-year helps more. With an ODCR the instances sit in your account "like your own data center".

4Corrections (checked on AWS pages, Oct 2026)

Instance families. P5 = 8× H100; P5e / P5en = 8× H200 (there's no "H300"). P6 = B200 / B300 (Blackwell); P6e UltraServers = GB200 / GB300 NVL72. P5 and P6: 2 TiB RAM, up to ~30 TB local NVMe (P5: 8× 3.84 TB).
EBS gp3 IOPS. Baseline is 3,000 IOPS, and you can provision up to 80,000 (at 500 IOPS per GiB), not "6,000 max". For more, or lower latency, use io2 Block Express or local NVMe.
Costs. His $100–150/hr and "Lustre ≈ 4× OpenZFS" are estimates. Check the current on-demand, Capacity Block and FSx prices before quoting a customer.
Also worth knowing: EC2 Capacity Blocks for ML reserve GPU clusters for days or weeks, often a better fit than an ODCR for short projects.
